# Сигнальный роутинг: от изменившихся файлов к категориям артефактов

Используй этот reference на шаге `signal_mapping`. Цель — превратить список изменившихся путей (`git diff --name-status <previous_baseline_commit>..HEAD`) в конкретный список категорий, которые нужно проверить глубже. Не анализируй файлы, которые не попали ни в одну категорию ниже и не относятся к чувствительным путям из раздела «Слабые сигналы».

Категории соответствуют пунктам `analysis_checklist` первичного анализа (см. таблицу соответствия в [checklist-targeted-deep-analysis.md](checklist-targeted-deep-analysis.md)).

## Основной источник: карта структуры репозитория

Если в архитектурном репозитории для этого репозитория уже есть `architecture/structure/<repo>.yml` (строится на этапе первичного наполнения архитектурного репозитория, пункт `repository_structure_mapping`) — она основной источник маршрутизации, а не общая glob-таблица ниже.

1. Загрузи `architecture/structure/<repo>.yml`.
2. Для каждого изменившегося пути найди покрывающую его запись в карте (путь из дельты начинается с одного из `paths` категории или совпадает с ним) и используй её категорию напрямую.
3. Таблица ниже («Fallback-таблица маршрутизации») применяется только к путям, которые карта не покрывает — это типично для репозиториев, где карта ещё не построена, или для путей, появившихся после последнего обновления карты (см. «Дрейф структуры» ниже).

Если карты для репозитория нет вообще (репозиторий анализировался до появления этого пункта в чеклисте первичного анализа, либо это repo, добавленный в scope позже) — используй только fallback-таблицу и зафиксируй в `notes` репозитория, что карту нужно построить отдельным проходом первичного анализа (пункт `repository_structure_mapping`) при следующей возможности.

## Дрейф структуры: новые/переименованные/удалённые пути

Карта валидна, только пока актуальна реальная раскладка каталогов. Перед применением карты проверь дрейф:

1. Из `git diff --name-status <previous_baseline_commit>..HEAD` выдели:
   - записи `A` (добавлен) — новый файл/директория верхнего уровня внутри пути, не покрытого ни одной категорией карты;
   - записи `D` (удалён) — был последним файлом в директории, которая была единственным основанием для путей какой-либо категории (категория осталась без актуальных путей);
   - записи `R0NN` (переименование) с низким similarity (NN заметно меньше 100, git фактически считает это новым файлом, а не чистым rename) — особенно если путь переехал в другую директорию верхнего уровня.
2. Если хотя бы одна из этих ситуаций обнаружена и затронутый путь не покрыт ни одной категорией карты — это дрейф структуры.
3. При обнаружении дрейфа зарегистрируй категорию `repository_structure_mapping` для репозитория (`update_guard.py signal --repo <repo> --add-category --category repository_structure_mapping --source-paths "<новые/удалённые/переехавшие пути>"`).
4. Закрывай эту категорию на шаге `targeted_deep_analysis` **первой**, до остальных категорий: актуализируй `architecture/structure/<repo>.yml` (добавь новые пути, убери исчезнувшие, перенеси переехавшие — см. `checklist-repository-structure-mapping.md`), и только после этого продолжай маршрутизацию остальной дельты по обновлённой карте.
5. Если дрейф затрагивает значительную часть репозитория (массовый рефакторинг раскладки) — рассмотри `diff_classification = significant` независимо от того, что говорят остальные сигналы, и явно отметь в `notes`, что карта структуры требует полного пересмотра, а не точечной правки.

### Frontend-специфичные сигналы

Backend-ориентированные строки выше не покрывают frontend-репозитории (web/mobile). Для них:

| Изменившийся путь / паттерн | Категория(и) |
| --- | --- |
| `**/app/**` (Next.js app router), `**/pages/**` (Next.js pages router / Nuxt), `**/routes/**` (React Router/Remix), `**/screens/**`, `**/navigators/**` / `**/navigation/**` (мобильная навигация) | `ui_screens_and_navigation`, `entrypoints_and_interfaces` |
| `**/api/`-клиенты, `**/services/api*`, сгенерированный SDK-клиент (`**/generated/**`, `**/__generated__/**`), `**/graphql/**` (`.graphql`-операции, query/mutation файлы), хуки `use*Query`/`use*Mutation` (React Query/SWR/RTK Query) | `integrations_and_dependencies`, `contracts_and_schemas` |
| `**/store/**`, `**/state/**`, Redux slices / Zustand stores / Pinia stores, если внутри есть вызовы API | `business_flow_orchestration`, `integrations_and_dependencies` |
| `**/components/**` без API-вызовов и без изменения роутинга | как правило, нет архитектурного эффекта — не открывай категорию только из-за этого, если других сигналов нет |

## Авто-генерируемые контракты — следи за источником, не за артефактом

В большинстве стеков `openapi.yml`/`swagger.json`/`*.proto`-stub генерируются из кода (FastAPI/Pydantic, drf-spectacular, NestJS Swagger-декораторы, springdoc, grpc-gateway annotations) и часто вообще не коммитятся в репозиторий — собираются в CI или на старте сервиса. В этом случае изменение самого файла контракта **не появится в дельте**, хотя контракт фактически изменился.

Поэтому:

- Если в репозитории нет закоммиченного файла контракта (`openapi.yml` и т.п.) — категория `contracts_and_schemas` маршрутизируется **только** через слой-источник: view/controller/router, serializer/schema/DTO, decorator-аннотации запроса/ответа (см. карту структуры или fallback-таблицу выше). Не жди изменения отдельного файла контракта — его не будет.
- Если файл контракта в репозитории всё же закоммичен и изменился **сам по себе**, без изменений в слое-источнике — это, скорее всего, результат пересборки (новая версия генератора, форматирование) и не несёт нового факта; перепроверь по факту, не открывай категорию только из-за этого файла.
- Если изменился и слой-источник, и закоммиченный файл контракта согласованно — это сильный сигнал, открывай категорию с уверенностью.
- При обновлении `architecture/contracts/<service>-*.yml` в этом skill ориентируйся на фактическое поведение кода (view/serializer/DTO), а не на устаревший или несвежий сгенерированный файл, если они расходятся.

## Слабые сигналы — не самодостаточны

Эти файлы могут изменяться без архитектурного эффекта. Используй их только как наводку, требующую перепроверки по коду:

- `README.md`, `CHANGELOG.md`, `docs/**` — обновляются и без изменения поведения; если других сигналов в дельте нет, не открывай категорию только из-за них.
- Комментарии в коде без изменения логики.
- Переименования файлов без изменения содержимого (`git diff --name-status` показывает `R100` — проверь, не `R0xx` с реальным изменением).
- Форматирование/линтинг (`git diff --stat` показывает много строк, но `git diff -w` — почти пусто).

## Семантика коммитов как дополнительный сигнал (Стратегия C)

`git log --oneline <previous_baseline_commit>..HEAD` — используй для приоритизации, **не** для замены анализа дельты:

- `feat:`, `BREAKING CHANGE`, `!:` (conventional commits breaking marker) — повышай приоритет репозитория в очереди `targeted_deep_analysis`, но категории всё равно определяй по карте структуры/файлам, а не по тексту коммита.
- `fix:`, `refactor:`, `chore:`, `test:` без изменения путей из карты/таблицы выше — обычно не требуют обновления архитектурных артефактов; зафиксируй это явно в `diff_classification = minor` и не открывай категории.
- Если сообщение коммита противоречит фактическому дифу файлов (например, `fix: typo`, но изменена миграция) — доверяй файлам, а не сообщению.

## Итог шага

Для каждого репозитория с `diff_classification != none` зафиксируй через `update_guard.py signal --repo <repo> --add-category --category <id> --source-paths "<path1,path2>"` все сработавшие категории — сначала `repository_structure_mapping`, если обнаружен дрейф, затем остальные. Если дельта есть, но ни одна категория не сработала и семантика коммитов не повышает приоритет — явно укажи в `notes` репозитория `"дельта не затрагивает архитектурно значимые пути"` и переходи к следующему репозиторию без открытия `targeted_deep_analysis` для него.
