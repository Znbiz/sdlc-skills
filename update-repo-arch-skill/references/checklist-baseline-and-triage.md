# Baseline и triage: подготовка дельты по каждому репозиторию

Используй этот reference на шагах `load_baseline`, `refresh_repositories`, `triage_repositories`.

## Шаг 1. Восстанови предыдущий baseline

`update-progress.json` — рабочий, одноразовый артефакт текущего прогона: успешно завершённый прогон удаляет его сам (`checklist-finalize-and-report.md`, шаг 6), поэтому в норме его не должно быть вообще. Если файл всё же найден от прерванного прогона — он не источник истины для baseline. Источник истины — закоммиченные артефакты самого архитектурного репозитория, которые `finalize_update` обязан обновлять при каждом прогоне.

Источники, в порядке приоритета:

1. `architecture/landscape.yaml`, поле `entities.services[].repository_state.head_commit` — основной источник, потому что закоммичен в архитектурный репозиторий и переживает удаление progress-файла.
2. `architecture/structure/<repo>.yml`, поле `analyzed_commit` — кросс-проверка: должен совпадать с `head_commit` из `landscape.yaml`. Если значения расходятся — это не повод выбрать одно из них произвольно: зафиксируй расхождение в `notes` репозитория и трактуй как `baseline_valid=false` (нужен полный пересмотр, а не точечная дельта), пока пользователь не подтвердит, какое значение верное.
3. `update-progress.json`, оставшийся от прерванного (не завершённого до `finalize_update`) прогона — используй только как дополнительную сверку или если он единственный доступный источник (например, `landscape.yaml` ещё не содержит `repository_state` для этого сервиса). Это сигнал, что предыдущий прогон не был завершён до конца — продолжи его (см. «Границы сессий» в `SKILL.md`), а не начинай новый.
4. Если предыдущего прогона update-репозитория не было вообще — `repo-initialization-progress.yaml`, оставшийся от первичного наполнения, поле `repositories[].analyzed_commit`.
5. Если ни одного из артефактов нет — это не сценарий для этого skill: остановись и предложи пользователю сначала провести первичное наполнение архитектурного репозитория.

Зафиксируй для каждого репозитория: `name`, `repository_url`, `local_path`, `main_branch`, `previous_baseline_commit`.

## Шаг 2. Обнови репозитории до актуального коммита

Для каждого репозитория из baseline:

- если локальной копии нет в `.temp/` — клонируй;
- переключись на `main_branch`, выполни `git fetch origin`, затем **обязательно** `git reset --hard origin/<main_branch>` и `git clean -fdx` — любые локальные изменения или незакоммиченные артефакты в `.temp/` затираются без предупреждения, копия временная и должна точно соответствовать GitLab; не используй `git pull` или merge-стратегии, которые могут оставить локальные расхождения;
- зафиксируй `new_baseline_commit` = текущий HEAD после обновления;
- если `previous_baseline_commit == new_baseline_commit` — изменений нет, репозиторий сразу получает `diff_classification = none` и пропускает все дальнейшие шаги, кроме финального отчёта.

## Шаг 3. Сформируй дельту

Для репозиториев, где коммиты различаются:

```
git diff --stat <previous_baseline_commit>..<new_baseline_commit>
git diff --name-status <previous_baseline_commit>..<new_baseline_commit>
git log --oneline <previous_baseline_commit>..<new_baseline_commit>
```

Сохрани результат `--name-status` как список путей для следующего шага (`signal_mapping`), а не пересказывай весь diff текстом.

## Шаг 4. Классифицируй дельту

- `none` — коммитов нет или единственные изменения — это форматирование/ребейз без изменения содержимого.
- `minor` — есть коммиты, но после применения [checklist-signal-routing.md](checklist-signal-routing.md) ни одна категория не сработала, и семантика коммитов не сигнализирует о breaking change.
- `significant` — сработала хотя бы одна категория сигналов, либо коммиты помечены как breaking/feat с изменением путей из routing-таблицы.

Зафиксируй классификацию через `update_guard.py repo --set-diff --repo <repo> --classification <none|minor|significant> --stat-summary "<краткое summary>"`.

## Правила

- Не пропускай шаг обновления до HEAD даже для репозиториев, которые "обычно не меняются" — десятки сервисов означают, что неожиданные изменения тоже возможны.
- Не классифицируй дельту как `none`, если `previous_baseline_commit` отсутствует в истории текущей ветки (значит, ветка была переписана — force-push, rebase). В этом случае пометь `diff_classification = significant` и явно зафиксируй в `notes`, что baseline невалиден и нужен полный пересмотр репозитория, а не точечная дельта.
- Triage всех репозиториев делай за один проход, прежде чем переходить к глубокому разбору любого из них — это и даёт масштабируемость на десятки сервисов.
