# Завершение прогона обновления

Используй этот reference на шаге `finalize_update`.

## Шаг 1. Обнови baseline во всех затронутых местах

Для каждого репозитория, у которого `diff_classification != none`, **обязательно** (не опционально) обнови оба закоммиченных артефакта — они источник истины для baseline следующего прогона, а не `update-progress.json`:

- `architecture/landscape.yaml` → `entities.services[].repository_state.head_commit` = `new_baseline_commit`;
- `architecture/structure/<repo>.yml` → `analyzed_commit` = `new_baseline_commit` (плюс `built_at` = дата прогона).

Дополнительно:

- если используется `repo-initialization-progress.yaml` как долгоживущий артефакт первичного наполнения — обнови в нём `analyzed_commit`;
- зафиксируй `new_baseline_commit` в `update-progress.json` текущего прогона — это рабочая копия для отладки и для шага `finalize_update`, но не замена обновления `landscape.yaml`/`structure/<repo>.yml` выше;
- если в `architecture/integrations/<service>.md` или другом артефакте в шапке явно фиксируется коммит-источник, обнови и его.

Репозитории с `diff_classification == none` тоже должны попасть в отчёт — явно как "без изменений", а не быть молча пропущены. Для них `landscape.yaml`/`structure/<repo>.yml` не трогай — коммит не менялся.

## Шаг 2. Создай release notes прогона — обязательный шаг, без него прогон не завершён

Заполни `assets/release-note-template.md` в новый файл `release-notes/<YYYY-MM-DD>.md` (дата завершения прогона; если в этот день уже есть файл — `<YYYY-MM-DD>-2.md` и т.д.). Это единственный отчётный документ прогона — раньше отчёт о прогоне и release notes были двумя разными файлами об одном и том же, теперь это один файл со всем содержимым:

- репозитории без изменений;
- репозитории с изменениями, затронутые категории и диапазон baseline-коммитов;
- обновлённые артефакты архитектурного репозитория — каждый как markdown-ссылка на сам файл (относительный путь от `release-notes/`), с коротким описанием, что изменилось;
- какие каскадные эффекты были обнаружены и как закрыты;
- новые пробелы / открытые вопросы, появившиеся в этом прогоне (со ссылкой на запись в `open-questions.md`);
- репозитории с невалидным baseline (force-push/rebase), которые требуют полного пересмотра, а не точечного обновления.

Это последний шаг, на котором весь контекст прогона ещё доступен в progress-файле — заполняй release notes сразу из него, не оставляй на потом и не пропускай, даже если прогон кажется "тривиальным" (например, единственный затронутый репозиторий).

## Шаг 3. Обнови open-questions.md

- Закрой вопросы, которые дельта явно разрешила (с пометкой, каким фактом и из какого репозитория).
- Добавь новые вопросы, обнаруженные в `cascade_check` или `targeted_deep_analysis`, если они не были закрыты в моменте.

## Шаг 4. Зафиксируй итоговый статус

- Переведи `update-progress.json` в `status: completed` через `update_guard.py advance --step finalize_update`.
- Заполни `resume_hint` — что проверять в следующий раз первым (например, репозитории с невалидным baseline, если такие остались). Это последнее, что читается из progress-файла перед его удалением на шаге 5 — `resume_hint` уже должен быть продублирован текстом в `release-notes/<YYYY-MM-DD>.md` (раздел «Следующий рекомендуемый шаг», шаг 2), а не существовать только в JSON, который скоро будет удалён.

## Шаг 5. Удали progress-файл текущего прогона

Прогон полностью завершён и зафиксирован в закоммиченных артефактах — `update-progress.json` больше не нужен:

- baseline сохранён в `architecture/landscape.yaml` и `architecture/structure/<repo>.yml` (шаг 1);
- полное summary прогона (что изменилось, каскады, пробелы, невалидный baseline, следующий шаг) — в `release-notes/<YYYY-MM-DD>.md` (шаг 2).

Удали файл `update-progress.json` (или путь, указанный в `--output` при `init`) после того, как шаги 1–4 выполнены и зафиксированы. Если шаги 1–4 не завершены — не удаляй файл, иначе прогон будет невозможно продолжить или диагностировать при прерывании.

## Правила

- Не считай прогон завершённым, если остался хотя бы один репозиторий с `diff_classification = significant`, у которого не закрыта ни одна категория.
- Не считай прогон завершённым, если для хотя бы одного репозитория с `diff_classification != none` не обновлены `architecture/landscape.yaml` (`repository_state.head_commit`) и `architecture/structure/<repo>.yml` (`analyzed_commit`) — без этого следующий прогон не сможет надёжно восстановить baseline, если `update-progress.json` будет утерян или перезаписан.
- Не считай прогон завершённым, если для него не создан файл `release-notes/<YYYY-MM-DD>.md` (шаг 2) — это единственное место, где остаётся summary прогона после удаления progress-файла.
- Не дописывай release notes прошлого прогона — каждый прогон получает свой новый файл, история прогонов хранится как набор файлов в `release-notes/`, а не как один растущий документ.
- Не удаляй `update-progress.json`, пока в нём остался хотя бы один незакрытый шаг или репозиторий — удаление допустимо только после `status: completed` и после того, как шаги 1–4 этого чеклиста зафиксированы в закоммиченных артефактах.
- Если в рамках прогона обнаружено, что нужно расширить scope (новый репозиторий, который ссылается на уже отслеживаемые, но сам не в списке) — зафиксируй это явно как рекомендацию пользователю, не добавляй репозиторий в scope самостоятельно.
