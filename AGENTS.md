# AGENTS.md

## Область проекта

Этот репозиторий — сервис.

Работай только внутри этого репозитория, если в задаче явно не сказано смотреть в другой репозиторий или общую продуктовую документацию.

## Правило навигации по коду

Для понимания устройства репозитория в первую очередь используй инструменты Codebase Memory MCP.

Codebase Memory предпочтительнее:
- поиска по файлам через grep
- последовательного чтения множества файлов
- разовых AST-скриптов
- широких проходов по файловой системе

Типовое сопоставление запросов и инструментов:
- «как устроен X?» → `get_architecture` или `search_graph`
- «кто вызывает эту функцию/метод?» → `trace_path(direction="inbound", mode="calls")`
- «что вызывает эта функция/метод?» → `trace_path(direction="outbound", mode="calls")`
- «что сломается, если я изменю это?» → `trace_path(direction="both", mode="calls")` и `query_graph`
- «найди точки входа / хендлеры / команды» → `search_graph`
- «прочитай точную реализацию символа» → `get_code_snippet`
- «нужен сложный структурный срез по графу» → `query_graph`

Переходи к `grep`/`read` только если:
- у Codebase Memory ещё нет индекса для этого репозитория
- файл находится вне индексируемого workspace
- нужен именно исходный текст файла для редактирования или точной проверки
- ищешь строковые литералы, markdown, shell-конфиги или точные текстовые совпадения вне графа

## Workflow индексации

Перед глубоким анализом в новой сессии:
1. Убедись, что для этого checkout есть отдельный индекс через `index_repository`.
2. Индексируй именно текущий репозиторий: `repo_path=/Users/aanekraso2/github.com/znbiz/sdlc`, `name="sdlc"`, `persistence=true`.
3. Для всех последующих вызовов используй точное значение `project`, которое вернул `index_repository`. Не выдумывай его вручную.
4. После крупных рефакторингов, переноса файлов, изменения сигнатур, маршрутов или зависимостей — переиндексируй снова.

Не предполагай, что граф актуален после переключения веток, `rebase` или большого `pull`.

## Workflow редактирования

Перед изменениями:
1. Получи графовый контекст для затрагиваемого символа или файла.
2. Определи вызывающих и вызываемые сущности, импорты, точки входа и связанные тесты через `search_graph` и `trace_path`.
3. Оцени радиус поражения через Codebase Memory перед изменением публичных интерфейсов.

После изменений:
1. Перезапусти релевантные тесты и линтеры.
2. Переиндексируй репозиторий, если изменилась структура файлов, импортов или публичных API.
3. Повтори проверку вызывающих и вызываемых, если изменение затронуло интерфейсы или поток управления.

## Работа с документацией

Этот репозиторий — часть общей архитектурной документации продукта.

Если задача касается сравнения кода и документации:
- сначала используй Codebase Memory для кода и только затем читай markdown-файлы напрямую
- не предполагай, что документация всегда актуальна
- явно фиксируй расхождения между реализацией и архитектурными документами

## Ожидания, специфичные для репозитория

Этот проект — сервис arch-docs. Обращай особое внимание на:
- поток запроса от API-слоя до выполнения CLI-команды
- авторизацию и жизненный цикл сессий для CLI агентов (`codex`, `claude code` и др.)
- границы контейнеров (Docker) и изоляцию workspace
- поведение subprocess/PTY внутри контейнера
- наблюдаемость: логирование, метрики, обработку ошибок
- границы безопасности вокруг секретов, команд и прав записи в workspace

## Безопасность и границы задач

По умолчанию не сканируй соседние репозитории.
Не опирайся на продуктовые предположения, если они не описаны явно.
Держи анализ локальным для этого репозитория, если явно не запросили cross-repo исследование.

## Предпочитаемый стиль работы

Работай точно и последовательно:
- сначала понимание структуры через Codebase Memory
- потом планирование
- затем изменения
- затем проверка

Избегай спекулятивных правок до того, как собран графовый контекст.
