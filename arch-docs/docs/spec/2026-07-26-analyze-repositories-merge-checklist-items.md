# Слить пер-item LLM-вызовы `analyze_repositories` в один вызов на репозиторий

**Статус:** done. Реализовано и покрыто тестами.

## Проблема

[2026-07-21-analyze-repositories-per-item-nodes.md](2026-07-21-analyze-repositories-per-item-nodes.md)
подняла цикл "один пункт чек-листа — один LLM-вызов" на уровень графа ради чекпоинта на границе
каждого пункта. Побочный эффект, не учтённый той спекой: каждый из ~20 пунктов чек-листа запускает
**независимую** агентную сессию без памяти о предыдущих вызовах (LangGraph-движок,
[2026-07-25-langgraph-api-agent-runner.md](2026-07-25-langgraph-api-agent-runner.md), раздел
"Что не входит" — resume/меж-вызовная память сознательно не проектировалась). Значит каждый пункт
заново проходит `list_directory`/`read_file` по всему репозиторию с нуля — 20-кратная переразведка
одного и того же кода. На реальном прогоне (проект `38d21ae5`, репозиторий `CodeGraph`) это оказалось
доминирующей причиной "долгого анализа репозитория", а не медленной модели как таковой.

Дополнительно наблюдалось: часть пунктов чек-листа стабильно не укладывалась в
`recursion_limit=50` (см. `langgraph_task_runner.py`) и проваливалась, граф ретраил (`_MAX_RETRY=3`)
тот же провальный пункт с тем же результатом — итог: пользователь видит шаг, зависший на десятках
провальных попыток подряд.

## Принятое решение

1. **`recursion_limit` 50 → 100** (`app/services/langgraph_task_runner.py`) — простое расширение
   бюджета tool-calling цикла для LangGraph-движка.
2. **Все pending-пункты чек-листа одного репозитория обрабатываются одним LLM-вызовом**, а не одним
   вызовом на пункт. `node_analyze_repositories_item` (`nodes.py`) собирает полный список через новую
   `pending_checklist_items()` (`domain/operations.py`, рефакторинг `next_pending_checklist_item()` —
   та же логика, но возвращает весь список, а не только первый элемент) и передаёт его в
   `build_step_prompt(..., checklist_item_ids=[...])` (`prompts.py`) — промпт получает по одному
   reference-разделу на каждый пункт и просит агента адресовать их все за один вызов.

**Осознанно принятый компромисс:** это разворачивает часть решения 2026-07-21 — чекпоинт снова на
уровне репозитория, а не пункта. При сбое внутри одного вызова (recursion-limit, таймаут, краш)
теряется прогресс по всем ещё не отмеченным пунктам этого репозитория, а не по одному пункту;
`_MAX_RETRY` ретраит весь пакет. Выбрано пользователем осознанно после явного объяснения этого
компромисса (альтернатива — пакеты по 3-5 пунктов — была предложена и отклонена в пользу полного
слияния).

## Как сохранена честность результата (не потерять проверку "файлы созданы")

Слияние вызовов создаёт риск, которого не было в пер-item дизайне: один вызов может по факту
покрыть не все запрошенные пункты (модель "устала"/не успела), но раньше отчёт был 1:1 с пунктом —
успешный вызов надёжно означал "этот пункт сделан". Чтобы не потерять эту гарантию:

- `LlmTaskResult.completed_checklist_items: list[str]` (новое поле, `domain/models.py`) — модель
  обязана в финальном JSON перечислить, какие именно ID пунктов она реально обработала. Промпт
  (`checklist_items_instruction` в `prompts.py`) явно требует не декларировать пункт, если он
  фактически не обработан.
- `node_analyze_repositories_item` вызывает `guard_service.complete_repository_item()` **только**
  для пунктов из пересечения "запрошено" ∩ `completed_checklist_items` — не для всех запрошенных.
  Частичный прогресс (модель закрыла 3 из 5) честно фиксируется, оставшиеся 2 пункта пересчитываются
  как pending на следующем входе в ноду (идемпотентно, без отдельного recovery-пути — тот же принцип,
  что и в 2026-07-21).
- Если `completed_checklist_items` пуст (ноль реального прогресса) — это **не** тихий no-op, а
  `step_error` (новый `_require_checklist_progress()`), попадающий в тот же retry/interrupt путь, что
  и любая другая ошибка шага. Без этой проверки нулевой прогресс без ошибки зациклил бы граф молча.
- `knowledge_service.collect_worker_artifacts()` (`knowledge.py`) — до этого изменения
  `analyze_repositories` вообще не вызывал эту функцию. Теперь `llm_result.created_artifacts`
  (самоотчёт модели о записанных файлах) регистрируется и диффится против снепшота (тот же механизм,
  что уже используют `refine_features`/`generate_release_notes`/`run_knowledge_lint`) — даёт
  audit-трейл ("что реально записано на диск"), которого для этого шага не было вовсе. Это проверка
  по самоотчёту модели, а не независимое сканирование файловой системы на соответствие ожидаемым
  путям по каждому пункту — такого маппинга "пункт чек-листа → ожидаемый путь артефакта" в кодовой
  базе нет и не вводился.

## Затронутые файлы

- `app/services/langgraph_task_runner.py` — `_RECURSION_LIMIT` 50 → 100.
- `app/workflows/init_arch/domain/models.py` — `LlmTaskResult.completed_checklist_items`.
- `app/services/task_runner.py` — парсинг `completed_checklist_items` из JSON-отчёта.
- `app/workflows/init_arch/domain/operations.py` — новая `pending_checklist_items()`,
  `next_pending_checklist_item()` теперь строится поверх неё.
- `app/workflows/init_arch/domain/__init__.py` — экспорт `pending_checklist_items`.
- `app/workflows/init_arch/prompts.py` — `build_step_prompt(..., checklist_item_ids=...)`, слитый
  reference-блок, `checklist_items_instruction`, поле `completed_checklist_items` в JSON-контракте.
- `app/workflows/init_arch/nodes.py` — `_build_task_request`/`_run_step_worker` пробрасывают
  `checklist_item_ids`; `node_analyze_repositories_item` переписан на один вызов на репозиторий;
  новый `_require_checklist_progress()`.
- Тесты: `tests/workflows/init_arch/test_nodes.py` (+2 новых теста, 3 переписаны),
  `tests/workflows/init_arch/test_prompts.py` (+1 тест), `tests/workflows/init_arch/
  test_analyze_repositories_integration.py` (2 теста переписаны под гранулярность "на репозиторий"),
  `tests/services/test_langgraph_task_runner.py` (recursion_limit 50 → 100).

## Не входит в эту итерацию

- Пакетное слияние (по 3-5 пунктов вместо всех сразу) — рассмотрено как альтернатива, отклонено
  пользователем в пользу полного слияния.
- Независимая проверка "для пункта X ожидается файл Y" по файловой системе — маппинга пункт→путь
  сегодня нет; `completed_checklist_items` полагается на самоотчёт модели, а не на детерминированную
  проверку диска.
