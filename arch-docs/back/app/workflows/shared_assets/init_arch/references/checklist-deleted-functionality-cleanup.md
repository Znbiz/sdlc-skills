# Пункт checklist: deleted_functionality_cleanup

Проверить, не осталась ли в документации `arch_repo_dir` описанная функциональность, которой больше нет в
этом репозитории за анализируемое окно, и почистить её. Это первый пункт чек-листа для этого репозитория —
выполняется раньше всех остальных, чтобы дальнейший анализ (структура, entrypoints, фичи и т.д.) шёл по уже
актуальной документации, а не рисковал принять устаревшее описание за всё ещё действующее.

## Шаги выполнения

1. Прочитать секцию «Удалённые пути» temporal delta текущего окна (полный список, без сокращения).
2. Отдельно прочитать секцию «Переименованные пути» — **не путай удаление с переименованием**: если путь
   есть в `renamed_paths`, функциональность не исчезла, она просто лежит по новому пути; ничего в
   документации удалять не нужно, максимум — обновить путь в трассировке, если он был указан буквально.
3. Для каждого пути из «Удалённые пути» найти его упоминания в документации: grep по полному пути и по
   basename файла/директории в `features/*.md` (секции «Трассировка реализации»), `architecture/*.md`,
   `architecture/contracts/*`, `architecture/storage/*`, `architecture/structure/*`, `wiki/*`.
4. Для каждого найденного упоминания определить масштаб удаления:
   - **Capability исчезла полностью** (все точки входа и ключевые файлы реализации, перечисленные в
     трассировке фичи/артефакта, входят в удалённые пути этого или предыдущих окон) — удали
     соответствующий раздел/файл, либо явно пометь его как `removed`/deprecated с датой и причиной (какой
     path исчез), и убери строку из `features-index.md`, если это был файл фичи.
   - **Capability изменилась частично** (удалена часть файлов, но не все) — обнови секцию трассировки,
     убрав мёртвые ссылки, и, если из-за удаления пропало единственное подтверждение (например,
     единственный тест или единственная точка входа) — понизь статус реализации по тому же правилу, что и в
     `feature_discovery_and_updates` (`implemented` → `partial`/`unknown`).
   - **Неочевидно**, относится ли найденное упоминание именно к этому удалённому пути (общий helper,
     переиспользуемый модуль, метафоричное совпадение имени) — не удаляй и не гадай; зафиксируй как
     `open_questions` с описанием, что именно неясно.
5. Зафиксировать в `notes` этого пункта: сколько удалённых путей обработано, что реально почищено (файлы,
   разделы, записи в `features-index.md`), что оставлено как `open_questions`. Если удалённых путей за это
   окно не было — явно зафиксировать «удалённых путей нет», а не оставлять пункт без содержательного вывода.

## Обязательные выходы

- Каждый путь из «Удалённые пути» либо сопоставлен с найденным упоминанием в документации и обработан (шаг
  4), либо явно отмечен как не имеющий отражения в документации (ничего не описывало этот код — тоже
  нормальный исход, не ошибка).
- Ни одно упоминание не удалено только на основании совпадения имени без проверки контекста (см. шаг 4,
  «неочевидно»).
- `notes` пункта содержит краткую сводку: сколько путей обработано, что почищено, что осталось открытым
  вопросом.

## Подводные камни

- Не удаляй документацию по переименованному (не удалённому) пути — сверяйся с `renamed_paths` перед каждой
  правкой.
- Не удаляй фичу/раздел целиком, если удалена только часть её реализации — понижай статус и обновляй
  трассировку вместо полного удаления.
- Не оставляй молчаливых пропусков: если сопоставление неочевидно, лучше зафиксировать `open_questions`, чем
  либо удалить актуальное описание, либо оставить документацию про давно не существующий код.
- Этот пункт не заменяет defense-in-depth проверки внутри остальных пунктов чек-листа (каждый из них тоже
  перепроверяет актуальность в своей предметной области, см. соответствующие reference-файлы) — если что-то
  было упущено здесь из-за широкого охвата, у профильного пункта будет ещё одна возможность это поймать.
